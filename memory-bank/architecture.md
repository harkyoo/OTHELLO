# 아키텍처 메모

## 문서 목적
- 이 문서는 현재 오델로 프로젝트의 파일 책임과 구조적 의도를 설명한다.
- 새로 합류하는 개발자가 어디에 무엇을 구현해야 하는지 빠르게 이해할 수 있도록 돕는다.

## 현재 아키텍처 상태
- 현재 구현은 구현 계획의 8단계까지 진행된 상태다.
- `src/game/` 하위의 규칙 계층 위에 `src/hooks/`와 `src/components/`가 올라간 형태로 PvP와 AI 대전을 모두 지원하는 UI가 구성되었다.
- AI 의사결정 계층이 `src/game/ai.js`로 분리되어 추가되었다.
- 이 시점의 핵심 목표는 이후 난이도 기능이 들어와도 컴포넌트가 규칙 세부사항이나 AI 계산 세부사항을 다시 갖지 않도록 경계를 유지하는 것이다.

## 상위 구조
```text
/
  index.html
  package.json
  vite.config.js
  src/
    App.jsx
    main.jsx
    components/
    game/
    hooks/
    styles/
  public/
  tests/
    game/
  memory-bank/
```

## 파일별 역할

### 루트 파일
- `package.json`
  - 프로젝트 의존성과 실행 스크립트를 관리한다.
  - 현재는 `dev`, `build`, `preview` 스크립트만 포함해 초기 개발 흐름을 단순하게 유지한다.
- `vite.config.js`
  - Vite와 React 플러그인을 연결하는 빌드 진입 설정이다.
- `index.html`
  - 브라우저 진입점이다.
  - React 앱이 마운트될 `#root` 컨테이너만 제공한다.
- `.gitignore`
  - 로컬 의존성 및 빌드 산출물을 버전 관리 대상에서 제외한다.

### `src/`
- `src/main.jsx`
  - React 애플리케이션의 실제 엔트리 포인트다.
  - 전역 CSS를 로드하고 `App`을 `#root`에 마운트한다.
- `src/App.jsx`
  - 현재는 실제 게임 화면 레이아웃을 조합하는 상위 컨테이너다.
  - 훅에서 받은 상태를 모드 선택기, 보드, 점수판, 상태바, 재시작 버튼에 전달한다.

### `src/styles/`
- `reset.css`
  - 브라우저 기본 스타일 차이를 줄이기 위한 최소 리셋을 담당한다.
- `globals.css`
  - 전역 토큰, 기본 배경, 상위 레이아웃, 타이포그래피를 담당한다.
- `board.css`
  - 오델로 보드, 셀, 돌, 유효 수 힌트, 마지막 착수 강조 스타일을 담당한다.
- `ui.css`
  - 점수판, 상태 카드, 재시작 버튼, 전체 레이아웃 보조 스타일을 담당한다.

### 예약된 디렉터리
- `src/components/`
  - 시각적 UI 컴포넌트를 둔다.
  - 현재 `GameModeSelector`, `Board`, `Cell`, `ScoreBoard`, `StatusBar`, `RestartButton`가 구현되어 있다.
- `src/game/`
  - 오델로 규칙 엔진을 둔다.
  - 현재 보드 생성, 유효 수 계산, 뒤집기, 패스, 종료 판정, AI 수 선택 등 순수 로직이 구현되어 있다.
- `src/hooks/`
  - React UI와 게임 로직을 연결하는 커스텀 훅을 둔다.
  - 현재 `useOthelloGame`이 상태 보관, 클릭 처리, 모드 전환, AI 자동 턴, 재시작, 파생 데이터 계산을 담당한다.
- `tests/game/`
  - 게임 로직 중심 테스트를 둔다.
  - 현재 보드 유틸리티, 규칙 엔진, 상태 전이 테스트가 구현되어 있다.
- `public/`
  - 정적 자산이 필요해질 경우 사용하는 디렉터리다.

### `src/game/` 세부 책임
- `constants.js`
  - 보드 크기, 플레이어, 방향 벡터, 초기 배치, 상태 메시지 상수를 제공한다.
- `board.js`
  - 빈 보드와 초기 보드를 생성하고, 셀 접근과 복사를 담당한다.
- `rules.js`
  - 특정 착수가 유효한지, 어떤 돌이 뒤집히는지, 점수와 승자가 누구인지 계산한다.
- `gameState.js`
  - 실제 플레이 흐름 기준으로 턴 진행, 패스, 종료 처리를 묶는다.
- `selectors.js`
  - UI가 직접 규칙 엔진 내부를 몰라도 점수와 유효 수 같은 파생 데이터를 읽을 수 있게 한다.
- `ai.js`
  - 현재 보드와 플레이어 기준으로 AI의 다음 수를 선택한다.
  - 규칙 엔진을 재사용하면서도 UI와 분리된 독립 의사결정 계층 역할을 한다.

### `src/components/` 세부 책임
- `GameModeSelector.jsx`
  - PvP와 AI 대전 모드 전환 UI를 담당한다.
- `Board.jsx`
  - 8x8 보드 렌더링과 셀 배치를 담당한다.
- `Cell.jsx`
  - 각 칸의 클릭 이벤트, 돌 렌더링, 유효 수 힌트, 마지막 수 강조, 비활성 상태를 담당한다.
- `ScoreBoard.jsx`
  - 흑/백 점수와 현재 턴 강조를 보여준다.
- `StatusBar.jsx`
  - 현재 메시지와 승패 요약을 표시한다.
- `RestartButton.jsx`
  - 재시작 액션의 전용 진입점이다.

### `src/hooks/` 세부 책임
- `useOthelloGame.js`
  - React 상태 초기화, `playTurn` 호출, 모드 전환, AI 턴 예약, 재시작, 파생 데이터 제공을 담당한다.
  - UI는 이 훅을 통해서만 게임 상태에 접근하도록 유지하는 편이 좋다.

### `tests/game/` 세부 책임
- `board.test.js`
  - 보드 생성과 셀 조작 유틸리티를 검증한다.
- `rules.test.js`
  - 유효 수 계산, 뒤집기, 점수, 승자 계산을 검증한다.
- `gameState.test.js`
  - 무효 착수, 턴 전환, 패스, 재시작 같은 상태 전이 흐름을 검증한다.
- `ai.test.js`
  - AI가 유효한 수를 선택하는지와 코너 우선 휴리스틱이 적용되는지 검증한다.

## 설계 의도

### 1. UI와 게임 규칙의 분리
- 가장 중요한 원칙은 React 컴포넌트 안에 오델로 규칙을 흩뿌리지 않는 것이다.
- 규칙 계산은 `src/game/`에서 끝내고, UI는 그 결과를 렌더링하는 데 집중해야 한다.
- 이 경계를 지켜야 AI 모드, 수순 기록, Undo 같은 기능을 뒤에 붙이기 쉬워진다.

### 2. 단일 진실 공급원 유지
- 게임의 실제 상태는 한 흐름에서만 관리되어야 한다.
- 보드, 현재 턴, 종료 여부 같은 핵심 상태는 커스텀 훅 또는 상태 전이 함수에서 일관되게 다루고, 점수나 유효 수는 파생 계산으로 처리하는 편이 유지보수에 유리하다.

### 3. 순수 함수 우선
- `src/game/` 하위 로직은 가능한 한 순수 함수로 작성해야 한다.
- 같은 입력에 같은 출력을 반환하는 구조를 유지하면 테스트가 쉬워지고, UI 결합 없이 규칙 엔진만 검증할 수 있다.

### 4. 상태 전이와 규칙 계산의 분리
- `rules.js`는 "무슨 일이 가능한가"를 계산하고, `gameState.js`는 "한 턴이 끝난 뒤 무슨 상태가 되는가"를 조합한다.
- 이 분리는 테스트 범위를 단순하게 만들고, 나중에 AI나 기록 기능이 들어올 때도 재사용성을 높인다.

### 5. 훅은 조립 계층, 컴포넌트는 표현 계층
- `useOthelloGame`은 상태와 이벤트 흐름을 모으는 조립 계층이다.
- 컴포넌트는 전달받은 값만 렌더링하고, 계산 로직은 훅과 `src/game/` 계층에 남겨야 유지보수가 쉽다.

### 6. 테스트는 규칙 계층부터 고정
- 오델로처럼 규칙 오류가 사용자 경험 전체를 깨뜨리는 프로젝트에서는 UI보다 규칙 계층 테스트를 먼저 두는 편이 효과적이다.
- 현재 구조는 `board.js`, `rules.js`, `gameState.js`를 독립적으로 검증할 수 있어 이후 리팩터링에도 비교적 안전하다.

### 7. AI는 규칙 엔진의 소비자여야 한다
- AI는 보드를 직접 조작하지 않고 `getValidMoves`, `getFlippableDiscs` 같은 기존 규칙 함수를 재사용해야 한다.
- 이렇게 해야 규칙이 바뀌어도 AI가 다른 판정을 하지 않게 된다.

### 8. 자동 턴 흐름은 훅에서 조율한다
- AI 차례 판단, 입력 잠금, 지연 실행은 `useOthelloGame`에서 조율하는 편이 적절하다.
- `gameState.js`는 계속 순수한 턴 전이 규칙만 담당하고, UI 타이밍은 훅에 남기는 것이 경계를 깔끔하게 유지한다.

## 다음 단계에서 추가될 책임
- 기록 또는 Undo 히스토리 계층
  - `gameState.js` 위에 상태 스냅샷 배열을 얹는 방식이 유력하다.
- 난이도별 AI 모듈
  - 현재 `ai.js`를 전략별 함수 집합으로 확장하는 방향이 적절하다.
- 선/후공 설정 계층
  - 훅의 모드 상태와 함께 시작 조건 설정으로 확장할 수 있다.

## AI 확장 방향 메모
- AI는 `rules.js`와 `board.js`를 재사용해야 한다.
- AI 후보 수 계산은 UI 훅이 아니라 `src/game/ai.js`에서 끝내는 편이 좋다.
- 훅은 "지금 AI가 둘 차례인지"와 "언제 자동 착수를 실행할지"만 담당해야 한다.
- 이렇게 유지하면 AI 난이도 추가나 다른 탐색 알고리즘 실험도 UI 수정 없이 가능하다.

## 유지보수 관점 통찰
- 지금처럼 초기에 디렉터리 경계를 먼저 고정해두면, 이후 기능 추가 시 파일 위치를 두고 흔들릴 가능성이 줄어든다.
- 보드 렌더링보다 규칙 엔진을 별도 계층으로 먼저 생각하면, 테스트와 디버깅 비용이 크게 줄어든다.
- MVP 단계에서는 파일 수가 조금 늘어나더라도 책임이 선명한 구성이 장기적으로 더 싸다.
- AI 추가 역시 규칙 계층과 UI 사이에 독립 모듈을 끼워 넣는 방식으로 처리해, 기존 코드의 변경 범위를 비교적 작게 유지할 수 있었다.
